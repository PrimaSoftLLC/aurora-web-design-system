# Видение дизайн-системы и Angular-библиотеки компонентов

**Назначение:** цель проекта и принятые решения

**Обновлено:** 3 ноября 2026 года

Этот документ фиксирует цель, согласованную структуру перехода и открытые вопросы. Он описывает конечное состояние отдельно от текущего устройства репозитория. Решения по деталям сборки, подключению библиотеки и переносу отдельных страниц согласуются до реализации.

Текущая готовность, оставшиеся задачи и последний подтверждённый объём проверок находятся в
[статусе миграции](angular-ui-kit-status.md). Устройство и команды сайта — в
[руководстве разработчика сайта](../../documentation-site/README.md).
Этот документ не ведёт хронологию реализации и запусков тестов.

## 1. Зачем нужна общая система

В компании есть несколько собственных приложений. Часть давно работает, часть только создаётся. Внешний вид и подходы к интерфейсам в них различаются. Цель общей работы — привести интерфейсы к согласованному визуальному стилю и дать командам общую основу для разработки.

В репозитории уже находится дизайн-система. Она задаёт визуальные правила: какие шрифты, цвета, размеры, интервалы и другие значения применять, для чего они предназначены и как ими пользоваться. В репозитории также есть документация и примеры, помогающие изучать эти правила.

На этой основе создаются переиспользуемые Angular-компоненты для Angular-приложений поддерживаемых версий. Компоненты должны соответствовать правилам дизайн-системы и позволять приложениям использовать одинаковые элементы интерфейса. Токены, визуальные правила, стили и шрифты существующей дизайн-системы принимаются как готовая основа. Перенос способа их отображения на сайте не означает изменение самих правил или значений.

## 2. Что понимается под дизайн-системой и токенами

Дизайн-система — это не только набор CSS-переменных. В данном репозитории она включает правила применения визуальных решений, исходные значения токенов, генерируемые стили, шрифты и ресурсы, поддержку вариантов оформления, документацию и инструменты вокруг них.

Токены — именованные значения дизайн-системы, например цвет, интервал или радиус. Пользовательское понимание о том, что токены обычно доступны в CSS как переменные, в целом верно. В этом репозитории первичный источник токенов — JSON-файл; CSS-переменные и связанные файлы создаются сборкой. Поэтому токен — это прежде всего согласованное именованное значение и его назначение, а CSS-переменная — один из способов предоставить это значение интерфейсу приложения.

Правила дизайн-системы считаются обязательными. Если документация назначает определённый шрифт, цветовой токен или способ применения, компоненты должны следовать этому правилу. Обсуждение реализации компонента не отменяет правил дизайн-системы.

В репозитории предусмотрены варианты бренда, светлого и тёмного оформления, а также плотности интерфейса. Компоненты и примеры должны корректно работать в поддерживаемых сочетаниях этих настроек.

Подключение дизайн-системы к приложению само по себе не означает, что вся существующая разметка приложения автоматически изменит вид. Приложение подключает стили и настройки дизайн-системы, а затем использует её токены, правила и компоненты там, где они предусмотрены.

## 3. Какая библиотека компонентов нужна

Планируется библиотека компонентов с заранее заданным оформлением Aurora, основанным на дизайн-системе. Приложение-потребитель подключает библиотеку и использует компоненты с этим оформлением. Это не проект нейтральных элементов управления, которые каждое приложение обязано заново стилизовать под себя.

Переопределения могут быть возможны там, где их допускают дизайн-система и API компонента, но они не меняют основную цель: компоненты поставляются с согласованным оформлением и следуют общей визуальной системе.

Компонент — самостоятельный, максимально общий элемент интерфейса. Он принимает параметры, влияющие на его представление или предусмотренное поведение. Ему неизвестно, в каком приложении и для какой бизнес-задачи его используют. Например, библиотечный компонент не должен знать о конкретной странице, модели данных или бизнес-процессе приложения.

Для каждого компонента отдельно обсуждаются назначение, публичные параметры и события, доступность, внутренние детали и то, что приложение вправе использовать напрямую. Сначала решение подробно обсуждается и согласуется, затем компонент реализуется. Не предполагается, что Angular API обязан повторять React API.

## 4. Один репозиторий и один устанавливаемый пакет

Желаемая модель — развивать дизайн-систему и Angular-библиотеку компонентов в одном репозитории и выпускать их одним пакетом. Приложение устанавливает одну зависимость и получает доступ к дизайн-системе и компонентам библиотеки через предусмотренные точки доступа.

Сохраняются существующие публичные пути пакета: Angular-компоненты доступны через `@primasoftllc/design-system/angular`, стили — через `@primasoftllc/design-system/styles.css`. Дизайн-система и библиотека собираются локально перед запуском или сборкой нового сайта. Публикация пакета для разработки сайта не нужна. Точные API будущих компонентов обсуждаются отдельно.

Пакет `@primasoftllc/design-system` распространяется через GitHub Packages.
Существующий порядок выпуска описан в [регламенте релизов](../release.md).
Изменение публикации согласуется отдельно от разработки компонентов.

## 5. Компоненты и React-примеры

В репозитории есть компоненты, написанные на React. Изначально они помогали показывать и оценивать применение дизайн-системы. Сейчас часть из них также входит в существующую сборку пакета, поэтому их нельзя считать только картинками или автоматически утверждённой спецификацией будущих Angular-компонентов.

React-компоненты полезны как справочный материал: по ним можно понять, какие элементы уже пробовали делать и как некоторые правила выглядят в коде. Однако состав будущей библиотеки, параметры Angular-компонентов и их поведение определяются отдельно. Переносить React API механически не требуется.

Angular-библиотека развивается по согласованным решениям о каждом компоненте.
В Angular 19 и новее избыточный `standalone: true` в реализациях и примерах не указывается.

Со временем React-реализации и связанные с ними демонстрации планируется заменять Angular-компонентами или примерами, собранными из Angular-компонентов. Специфические элементы, нужные только для демонстрации или одному приложению, не обязательно должны становиться публичными библиотечными компонентами. Например, сложный заголовок конкретного приложения может быть показан как пример композиции общих элементов, но не включён в библиотеку как самостоятельный универсальный компонент.

Конечное состояние не содержит React: удаляются React-компоненты, их публичные экспорты, примеры, сборочные инструменты и зависимости. Во время перехода они остаются необходимыми существующему сайту. Состав экспортируемой Angular-библиотеки обсуждается отдельно от состава демонстраций. Например, пример композиции кнопки и иконки не означает автоматического решения выпускать отдельный IconButton.

## 6. Единый сайт документации и примеров

Желаемый результат — один сайт с двумя понятными частями:

1. **Дизайн-система.** Правила, токены и темы, которые уже представлены на текущем сайте.
2. **Библиотека компонентов.** Отдельный пункт навигации, ведущий к каталогу компонентов.

Новый сайт — полноценное Angular-приложение в папке `documentation-site/`, без React и iframe. У него две основные страницы: главная с описанием дизайн-системы и `components` с каталогом компонентов. Внешний вид, содержание и возможности существующего сайта сохраняются при переносе; изменения отдельных возможностей обсуждаются отдельно.

В каталоге компонентов пользователь выбирает элемент в левой навигации. В основной области он видит назначение компонента, актуальные параметры, рабочие примеры и код, достаточный для понимания и воспроизведения этих примеров. Страница должна помогать как при просмотре готовых компонентов, так и при разработке конкретного компонента.

Каталог нужен в двух ситуациях:

- **Разработка в этом репозитории.** Разработчик запускает локальную команду и видит актуальный результат работы. После изменения компонента страница обновляется без ручной пересборки каждого отдельного примера.
- **Использование в приложении.** Разработчик приложения открывает опубликованную документацию и находит доступные компоненты, их назначение, параметры и примеры, не поднимая отдельное приложение только ради просмотра справки.

В качестве достаточного первоначального способа публикации каталога для приложений рассматривается GitHub Pages. Там должна показываться актуальная опубликованная версия документации. История документации по версиям и переключатель между версиями на этом этапе не требуются.

Демонстрационные примеры должны быть написаны на Angular либо собраны из Angular-компонентов. Они показывают общие элементы и их применение; бизнес-логика конкретного приложения в библиотечные компоненты не переносится.

Работающие демонстрации хранятся в приложении нового сайта и не попадают в устанавливаемую библиотеку. Правила, значения токенов, стили и шрифты берутся из существующей дизайн-системы; отдельная версия токенов не создаётся. При переносе страницы её текст и оформление временно копируются в Angular-шаблон. Пока существуют оба сайта, такие копии допустимы; они не требуют отдельной инфраструктуры синхронизации. Изменения общих правил при необходимости согласуются для обоих вариантов, а старые страницы удаляются при завершении миграции. Нужные демонстрации страниц основ также реализуются на Angular или обычной разметкой с токенами внутри нового сайта.

Новый сайт разрабатывается рядом со старым. На время перехода вводятся отдельные команды разработки и сборки нового сайта и отдельный каталог результата. Существующие команды, сборка старого сайта и публикация продолжают работать до согласованного переключения. React удаляется после замены его применений.

## 7. Приложения-потребители

Сейчас нет приложения компании, которое уже использует эту библиотеку и дизайн-систему в реальной работе. Поэтому первые проверки интеграции с приложением-потребителем появятся после того, как будет готова начальная группа Angular-компонентов.

Не требуется сейчас выбирать первое приложение для редизайна. Задача текущего репозитория — подготовить дизайн-систему, библиотеку компонентов, их примеры и способ распространения. Подключение библиотеки к существующему приложению будет отдельным этапом, когда появится подходящее приложение и достаточный набор компонентов.

## 8. Ветки, проверка изменений и публикация

Работа ведётся в форке репозитория. Для компонента разработчик создаёт отдельную ветку, вносит изменения и отправляет их в свой репозиторий, после чего открывает запрос на слияние в ветку `develop` основного репозитория PrimaSoftLLC.

Слияние обычной рабочей задачи в `develop` само по себе не должно считаться командой выпуска пакета. Выпуск запускает ответственный разработчик осознанным ручным действием. Команды могут автоматизировать сборку и проверки, но автоматизация не должна лишать разработчика контроля над моментом публикации.

В репозитории уже есть рабочий процесс выпуска, связанный с веткой `master`, и рабочий процесс публикации GitHub Pages, связанный с тегом версии. Точный путь от проверенного изменения до ручного запуска выпуска и публикации необходимо внимательно разобрать при обсуждении архитектуры и процесса релиза. В этом документе не утверждается, что текущая автоматизация уже полностью соответствует желаемому ручному контролю.

## 9. Границы архитектуры

- `design-system/` — канонические токены, стили, шрифты и ресурсы; на время перехода
  здесь также остаются React-компоненты и старый каталог.
- `ng-ui-kit/` — переиспользуемые Angular-компоненты и проверки устанавливаемой библиотеки.
- `documentation-site/` — Angular-приложение документации и демонстраций.
- Зависимости нового сайта, npm-команды и lock-файл находятся в корне репозитория.
  Отдельный package.json сайта не вводится.
- Сайт импортирует библиотеку через публичный `/angular`, стили через `/styles.css`.
  Для dev и production используются одинаковые импорты в локально собранный `dist/`.
  Публиковать пакет или подменять импорты прямыми ссылками на исходники для сайта не нужно.
- Результат сайта отделён от пакета библиотеки. Приложения-потребители не получают
  исходники документации, её примеры и Angular-инструментарий разработки сайта.
- Независимые приложения в `ng-ui-kit/tests/consumers/` устанавливают tarball,
  а не используют aliases на исходники. Проверка сайта не заменяет проверку поставки.

## 10. Организация сайта и примеров

- Главная `/` открывается сразу и по логотипу; `/components` — отдельный каталог.
  У статей и компонентов собственные адреса. Hash-routing не используется.
- Один пункт меню — один маршрут — один PageComponent. Группы меню сами по себе
  не требуют отдельных страниц. Общий компонент со switch по всем страницам не вводится.
- Общая оболочка ArticleLayout отвечает за заголовок, размещение контента и оглавление.
  Содержимое страниц пишется непосредственно; повторения выносятся по фактической необходимости.
- Документация остаётся на русском и на поверхности DEFAULT/light/cozy.
  Query-параметры theme, appearance и density меняют демонстрации, а не оформление текста статьи.
  Оглавление и ссылки разделов используют стабильные id заголовков.
- Примеры страниц находятся в приложении сайта. Библиотечные имена начинаются с Ds,
  компоненты страниц содержат Page, внутренние блоки сайта не экспортируются как UI kit.
- ExampleBlock, CodeBlock и Disclosure имеют отдельные обязанности. Код передаётся
  типизированными сниппетами рядом со страницей; раскрытие CodeBlock не связано с Disclosure.
- Обычные таблицы документации остаются HTML-таблицами с общими стилями.
  Наличие таблицы в статье само по себе не требует DsTable.
- Развёрнутые шаблоны и стили хранятся отдельно; сайт использует SCSS без второй системы токенов.
  Подробности форматирования и общих блоков — в README сайта.
- Служебные документы могут иметь отдельный центрированный макет без левого меню,
  со ссылкой «На главную». Они не обязаны становиться пунктами каталога.

## 11. Правила постепенного переноса

Перенос сохраняет правила, смысл, структуру и оформление статей. Различия оформления
конкретных раскрывашек и примеров сверяются с оригиналом, а не заменяются одним вариантом автоматически.
Согласованная порция работы заканчивается остановкой для просмотра.

Если для полного сценария не хватает компонентов, остаётся явная временная заглушка.
Не требуется имитировать отсутствующий компонент или создавать его без обсуждения.
После добавления компонента проверяются и заглушки, и временные нативные элементы в статьях;
замена выполняется при совпадении назначения и поведения.

Жёлтая подсветка migration-placeholder — временная отметка незавершённого содержимого.
Её контраст отдельно не дорабатывается; отметка и узкое исключение проверки удаляются
при заполнении примера. Остальные требования доступности остаются обязательными.

Состав специализированных примеров, карты и эталонных экранов согласуется с заказчиком.
Композиция общих компонентов не обязана становиться публичным компонентом.
Калькулятор палитры рассматривается отдельно: его алгоритм не перерабатывается без обсуждения.

## 12. Дальнейший переход

Старый и новый сайты работают параллельно до согласованного переключения.
Сначала дополняется Angular-библиотека и подходящие демонстрации, затем согласуются
оставшиеся специализированные материалы и проверяется замена старого сайта.
Переключение основных команд, публикации Pages и удаление React — отдельные этапы.

Связка Form field и dsInput уже добавлена. Перед PR основы завершаются её визуальная
проверка, проверка установленного пакета в поддерживаемых Angular-потребителях
и итоговая проверка ветки. Далее применяется порядок «один компонент — одна ветка».
Подготовка PR, релиз и push выполняются только по соответствующему поручению.

Логику компонентов проверяют типизированные *.spec.ts через Angular TestBed,
Karma и Jasmine; браузерные тесты
проверяют реальный DOM, стили, клавиатуру, доступность и установленный пакет.
Проверки страниц отвечают за демонстрации и оболочку. Для unit-тестов есть две
общие команды: библиотеки и сайта, со стандартными параметрами Angular CLI.
Дополнительная система запуска и кеширования браузерных проверок не вводится.
Подробности — в [руководстве проверок](../../ng-ui-kit/tests/README.md).
