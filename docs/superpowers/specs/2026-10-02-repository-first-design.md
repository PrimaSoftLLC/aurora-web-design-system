# Самостоятельная дизайн-система в репозитории

Дата: 2026-10-02.
Статус: разделы согласованы в разговоре; письменная спецификация ожидает ревью пользователя.
Исходная база исследования: `develop`, коммит `8bf5c4d`, версия пакета `3.0.1`.

## 1. Цель и согласованные ограничения

Репозиторий становится единственным источником дизайн-системы Aurora. Разработка,
просмотр примеров, проверки и сборка пакета работают без Claude и его артефактов.
Цель — сократить ручную поддержку и упростить подключение системы, сохранив внешний
вид, поведение и совместимость существующих потребителей.

Пользователь выбрал перенос существующей системы в самостоятельную сборку.
Миграция в Storybook и создание нового конструктора компонентов не входят в работу.
Существующие React-компоненты, HTML-примеры и содержательная документация сохраняются.

Успех означает:

- сборка воспроизводится из чистого checkout после установки зависимостей;
- значения токенов, библиотека компонентов и материалы каталога имеют явные источники;
- превью и UI-тесты используют сборку актуальных исходников;
- каталог предоставляет поиск, документацию и сравнение режимов без CDN;
- старые подключения пакета продолжают работать, новое подключение Angular проще;
- новая инструкция описывает один рекомендуемый путь, старый путь остаётся совместимым.

Публикация пакета, перенос приложений-потребителей и редизайн интерфейса не входят
в реализацию. Удалять публичные имена ради чистоты API не требуется.

## 2. Текущее устройство и причины изменений

`CLAUDE.md`, `CONTRIBUTING.md` и `SYNC.md` предписывают редактировать систему
в артефакте Claude и переносить изменения в Git. Обратные изменения перечисляются
вручную в `SYNC.md`. Решение пользователя заменяет этот рабочий процесс.

Сейчас `tools/build.js` собирает CSS из `tokens.css`, `tokens/scoped.css`,
`components/bundle.css` и локальных объявлений шрифтов. В сборке есть преобразование
селекторов артефакта и проверка копий токенов. Часть повторных объявлений необходима
для пересчёта переменных при вложенных темах: удалять их по текстовому сходству нельзя.

React-исходники поставляются из `components/src`, а UI-тесты исполняют сохранённый
`components/bundle.js`. Текущая команда сборки не создаёт этот JS-бандл.
Некоторые HTML-превью рассчитывают на ресурсы, которые подключал артефакт.

Angular-слой подключается через ручной `paths` в приложении. Его общий индекс
экспортирует интеграцию ECharts, поэтому даже базовому слою требуются типы ECharts.
Сервис темы сейчас нужно внедрить отдельно, чтобы запустить применение атрибутов.

Документация содержит повторяющиеся инструкции и устаревшие сведения: ссылки
на отсутствующие файлы фокуса и полей, неверное число карточек и страницы API
без таблицы props при наличии отдельных деклараций типов.

Предварительный запуск `npm test` прошёл сборку, 75 проверок линтера и четыре
последующих набора UI-проверок. Затем `guard-bash.test.js` завершился с 21 сбоем.
Причина не установлена; более поздние проверки этой цепочки не выполнялись.
Это наблюдение, а не подтверждение полностью зелёной исходной базы.

## 3. Источники и границы генерации

| Область | Редактируемый источник | Результаты |
|---|---|---|
| Токены | `tokens.json`; отдельные исходные данные плотности для значений, отсутствующих в его публичной схеме | CSS токенов, список линтера, справочник |
| Правила CSS | Исходные стили фокуса, полей, анимации и других общих правил | `dist/styles.css` |
| Компоненты | Текущие файлы `components/src/components` и их декларации типов | JS для каталога и тестов, таблицы props |
| Примеры | Существующие HTML-превью и их метаданные | Самостоятельные страницы каталога |
| Пояснения | Markdown рядом с компонентами и общие руководства | Документация каталога |
| Angular | TypeScript сервиса, директивы, типов и отдельного моста ECharts | Новые входы пакета и прежние совместимые пути |

У каждого токена и каждого его варианта ровно одно редактируемое определение.
Повторные объявления в выходном CSS допустимы, когда нужны каскаду, но создаются
генератором. Существующую публичную структуру `tokens.json` сохраняем; внутренние
данные плотности не требуют ломать её. Связанные значения выражаем ссылками,
а не независимыми копиями литералов.

При переносе значения сверяются с фактически работающим CSS исходной версии.
Если JSON и runtime расходятся, расхождение разбирается явно: миграция не должна
молча менять внешний вид под видом исправления генерации.

CSS для приложения и каталога строится из одной модели тем. Поддерживаются
независимые `data-ds-theme`, `data-ds-appearance`, `data-ds-density`, включая
локальные переопределения и вложенные скоупы. Селекторы рамок Claude не являются
основой нового механизма.

Собранные бандлы, индексы и справочники не являются редактируемыми источниками.
Предпочтительное место выходных файлов — игнорируемые каталоги сборки. Если
исторический путь нужен совместимости, сборка создаёт файл по этому пути.
Чистый checkout не должен зависеть от сохранённых результатов прежней сборки.

Пакет продолжает поставлять существующие React-входы; новый бандл каталога
получается из тех же исходников. Доступ через старый глобальный namespace
разрешён только как автоматически создаваемый адаптер для сохранённых примеров.
`manifest.json` артефакта, blob-ID и старые хеши не требуются для новой сборки.

## 4. Команды, зависимости и ошибки

| Команда | Контракт |
|---|---|
| `npm run dev` | Запускает локальный каталог и обновляет его при изменении исходников |
| `npm run build` | Собирает пакет и статический каталог из исходников |
| `npm run verify` | Выполняет сборку и обязательные проверки поведения, оформления и поставки |

Node и npm запускаются через mise с версией проекта. Зависимости фиксируются
lock-файлом. После установки зависимостей сборка и работа каталога не обращаются
за React, Babel, шрифтами или иными runtime-ресурсами к CDN.
JSX в примерах преобразуется при сборке, а не браузерным компилятором с CDN.
Каталог и его служебные ресурсы не должны попадать в npm-пакет приложения.

Генераторы останавливаются с ненулевым кодом и сообщением с путём и именем
проблемной сущности при дублирующемся токене, неразрешимой ссылке, неверных
метаданных, отсутствующем ресурсе или несовместимом описании API.
Циклические ссылки токенов также считаются ошибкой.
В режиме разработки ошибка отображается явно; устаревшая сборка не выдаётся
за успешный результат новой правки. Одинаковые входы дают одинаковый результат
без дат и случайных идентификаторов в генерируемом содержимом.

## 5. Каталог и документация

Каталог — простой локальный сайт и статическая сборка с навигацией и поиском
по компонентам, основам и эталонным экранам. Развёртывание публичного сайта
не требуется. Все 68 обнаруженных превью учитываются при миграции;
количество и навигация далее выводятся из фактического состава материалов.

Страница компонента содержит живые примеры, правила применения и таблицу props.
Имена, типы и обязательность props берутся из деклараций. Значения по умолчанию
проверяются по реализации; если значение не удаётся извлечь однозначно,
оно описывается явно и проверяется, а не угадывается генератором.
Расхождения деклараций и реализации устраняются без удаления существующих props.

Существующие метаданные карточек служат исходным материалом для индекса.
Отдельный список страниц, который приходится обновлять вручную, не вводится.
Связанные страницы группируются в семейства «Выбор», «Шапка», «Графики»;
самостоятельные примеры и объяснения внутри этих семейств сохраняются.
Прямые ссылки на прежние карточки получают рабочую страницу либо перенаправление.

Бренд, оформление и плотность переключаются независимо. Отдельный режим
сравнения показывает четыре принятые комбинации рядом:

- DEFAULT / light / cozy;
- DEFAULT / dark / compact;
- RED2 / light / cozy;
- RED2 / dark / compact.

Страницы, специально демонстрирующие несколько тем, сохраняют собственные
локальные скоупы. Переключатели каталога не должны разрушать смысл таких примеров.
Monitoring, Admin и AppShell остаются отдельным разделом эталонных экранов.
Навигация и переключатели доступны с клавиатуры и имеют понятные подписи.

Маршрут документации: краткий README → `getting-started.md` → каталог и API.
`getting-started.md` — единственная пошаговая инструкция подключения.
`ANGULAR.md` описывает особенности интеграции и совместимости, не дублирует шаги.
Архитектурные решения сохраняются рядом с соответствующими темами.
Сгенерированная документация больше не содержит инструкций `x-import` для Claude.
Редактор произвольных props и конструктор экранов не входят в первую версию.

## 6. Angular и совместимость

Новые публичные входы:

- `@primasoftllc/design-system/angular`: настройки, сервис темы, директива и типы;
- `@primasoftllc/design-system/angular/echarts`: функции интеграции графиков.

Первый вход не импортирует ECharts, в том числе его типы. Приложение без графиков
собирается без установленного ECharts. Второй вход явно требует эту зависимость.
Angular-выходы публикуются в формате, который приложение может использовать
без алиаса на исходники; минимальная поддерживаемая версия Angular остаётся 19.

`provideAurora(...)` инициирует применение настроек без дополнительного внедрения
сервиса ради его создания. Сохраняются конфигурация, методы сервиса, значения
по умолчанию и ключи localStorage. Пользовательские настройки оформления
и плотности сохраняют нынешний приоритет; тема остаётся настройкой арендатора.
`theme-*` приложения и `FRONT_BRAND` продолжают работать вместе с атрибутами системы.

Старый путь `components/src/templates/angular/index.ts`, используемый через
`tsconfig.paths`, продолжает поставляться со старым набором экспортов, включая
графики. Его прежняя зависимость от ECharts допустима: освобождение от неё
получает новый базовый вход. Обе формы подключения используют одну реализацию,
без самостоятельных копий сервиса и идентификаторов внедрения зависимостей.

При переходе потребитель удаляет ручной алиас; импорты функций графиков переносит
в отдельный вход. Старые формы вызова `provideAurora` и отдельное внедрение
сервиса остаются допустимыми. Существующий контракт возврата провайдеров сохраняется.

Сохраняются существующие exports пакета, пути CSS из `angular.json`, React-имена,
props, CSS-переменные, брендовые наборы, плотности и поведение компонентов.
Пути исходников, описанные в нынешних инструкциях подключения, также учитываются
в проверке совместимости. Публичная схема `tokens.json` остаётся совместимой.

`DsSelectBox` и `DsCheckButton` описываются одной основной карточкой с объяснением
обоих имён. Обёртка остаётся, её props и поведение не меняются. Разные сценарии
`DsBulkBar` и `DsSelectionBar` сохраняются отдельными компонентами.
Для данной работы не требуется major-выпуск ради удаления старого API.

## 7. Проверки и критерии приёмки

Перед заменой генераторов фиксируется эталон исходной версии из Git. Снимки
и вычисленные значения не генерируются заново из новой реализации как собственный
эталон. Для отсутствующих самостоятельных превью допускается адаптер подключения
ресурсов исходной версии; он не меняет код и оформление проверяемых компонентов.

| Область | Обязательная проверка |
|---|---|
| Оформление | Все перенесённые превью и эталонные экраны сравниваются до/после в четырёх комбинациях |
| Токены | Вычисленные значения публичных переменных совпадают с эталоном; отдельно проверяются вложенные темы и плотность без темы-предка |
| Независимость скоупов | Проверяются все восемь комбинаций двух брендов, оформлений и плотностей, а также существующие случаи вложенности |
| Поведение | Сохранены тесты клавиатуры, фокуса, выбора, диалогов, загрузки и локализации; они исполняют свежий JS-бандл |
| Доступность | Проверяются контраст токенов, AXE и ручной проход клавиатурой по каталогу и репрезентативным интерактивным примерам |
| Поставка | Проверяется реальный tarball, exports, пути ресурсов и отсутствие файлов каталога в пакете |
| Angular | Собираются минимальные потребители со старым алиасом, новым базовым входом без ECharts и новым входом графиков с ECharts |
| Документация | Проверяются внутренние ссылки, состав карточек и соответствие таблиц props декларациям и реализации |
| Самостоятельность | Чистая сборка без старых бандлов; каталог не делает запросов к CDN и не требует файлов артефакта |

Визуальные сравнения выполняются в одинаковом браузере и окружении, с локальными
шрифтами, фиксированными данными и стабилизированными анимациями. Технические
отличия снимков разбираются; массовое обновление эталонов вместо проверки
не считается приёмкой. Изменение цветов, размеров, раскладки или поведения
требует отдельного решения и не маскируется миграцией сборки.

Первым действием реализации диагностируется сбой guard-тестов: выбор `bash`,
доступность его зависимостей, stderr и фактический результат хука.
Обязательная проверка должна проходить в поддерживаемом локальном окружении
и CI. Если предпосылка отсутствует, выдаётся понятная ошибка с ненулевым кодом;
молчаливый пропуск не считается успешной проверкой.
Привязка защитных механизмов к Claude заменяется настройками рабочего инструмента,
но ограничения публикации сохраняются. Команды из тестовых кейсов передаются
хуку как данные, не исполняются как реальные публикации или push.

## 8. Этапы перехода и завершение

### Этап 1. Источники, сборка, самостоятельный каталог

Установить проверяемую исходную базу и эталоны. Перенести генерацию токенов
и JS в репозиторий, подключить тесты к свежей сборке, обеспечить самостоятельную
работу всех примеров и базовую навигацию каталога. Команды сборки и разработки
становятся воспроизводимыми. Правила репозитория и защиты агентов обновляются
уже на этом этапе, чтобы не предписывать возврат изменений в Claude.

Выход этапа: пакет со старым контрактом и рабочий каталог собираются без артефакта;
проверки поведения, токенов, оформления и старой поставки проходят.

### Этап 2. Angular и подключение

Добавить два новых входа, автоматическую инициализацию и проверки совместимости.
Обновить единственную инструкцию подключения; задокументировать необязательный
переход со старого алиаса. Старые проекты не требуют немедленного обновления.

Выход этапа: три варианта приложения-потребителя собираются из tarball,
базовый новый вариант не зависит от ECharts.

### Этап 3. Каталог и документация

Сгруппировать карточки, завершить поиск и справочник API, сохранить прямые ссылки,
убрать дубли инструкций и устаревшие материалы синхронизации. Правила и полезные
пояснения переносятся в актуальную документацию, а не исчезают вместе со старыми файлами.

Выход этапа: все согласованные возможности каталога доступны, ссылки и API
проверяются автоматически, инструкция не требует действий в Claude.

Каждый этап оформляется отдельным проверяемым коммитом или PR; внутри большого
этапа допустимы небольшие последовательные коммиты. Публикация и перенос
потребителей выполняются отдельно по действующему процессу релиза.
Изменения документируются в CHANGELOG и в правилах работы с репозиторием.

После ревью этой письменной спецификации составляется план реализации.
Согласование разделов в разговоре не заменяет ревью файла и плана.
